# 信管 Agent 助手 - 面试深度拷打 Q&A

---

## 一、ReAct 自主规划与工具协同

### Q1：你说你自主实现了 ReAct 模式，能详细说说你的 ReAct 循环是怎么设计的吗？Think 和 Act 具体做了什么？

**回答：**

我的 ReAct 实现是一个三层继承体系：`BaseAgent → ReActAgent → ToolCallAgent → YuManus`。

- **BaseAgent**：定义了整个执行框架，包括状态管理（IDLE → RUNNING → FINISHED/ERROR）、步数控制（maxSteps=10）、以及 `execute()` 统一入口方法。
- **ReActAgent**：定义了 `think()` + `act()` 的抽象接口，并在 `step()` 方法中串联：先调用 think() 判断是否需要行动，如果返回 true 则执行 act()。
- **ToolCallAgent**：具体实现了 think 和 act：
  - **Think 阶段**：将当前消息上下文（包含 systemPrompt + nextStepPrompt + 历史消息）组成 Prompt 发送给 LLM，LLM 返回时会附带 toolCalls 列表——即它决定调用哪些工具、传什么参数。如果 toolCalls 为空，说明 LLM 认为任务已完成，返回 false 不再行动。
  - **Act 阶段**：调用 `ToolCallingManager.executeToolCalls()` 执行 LLM 选定的工具，获取工具返回结果后追加到消息上下文。如果检测到调用了 `doTerminate` 终止工具，则将状态设为 FINISHED，跳出循环。

整个循环最多执行 10 步，每步都是"思考→选工具→执行→结果反馈给 LLM→再思考"的闭环，直到 LLM 主动调用终止工具或达到步数上限。

---

### Q2：你为什么要禁用 Spring AI 内置的工具调用机制？自己维护消息上下文有什么好处？

**回答：**

Spring AI 内置的 Tool Calling 机制是"一次调用、自动执行"的模式——LLM 返回工具调用后框架自动执行并把结果拼回去直接生成最终回复。这对简单场景够用，但不适合 ReAct 模式。

ReAct 需要**多轮循环决策**：LLM 拿到工具结果后可能还需要继续推理、调用其他工具、甚至修正之前的判断。如果用内置机制，一次调用就结束了，没有"循环"的能力。

所以我通过 `DashScopeChatOptions.withProxyToolCalls(true)` 禁用自动执行，改为自己维护消息列表（messageList），这样可以：
1. 在每一步的 think 后拿到工具选择结果，记录日志、做决策
2. 在 act 执行工具后把结果写回上下文，让下一轮 think 能看到历史
3. 通过检测 TerminateTool 来自主决定何时结束，而不是框架替我决定

---

### Q3：你提到集成了 MCP 协议，为什么要把部分工具拆到独立的 MCP Server？这和本地 Tool Calling 有什么区别？

**回答：**

拆分的核心考虑是**关注点分离和独立部署**：

- 联网搜索（WebSearch）、网页抓取（WebScraping）、PDF 生成、资源下载这些工具涉及网络 I/O、外部 API 调用，它们的依赖和生命周期跟核心 Agent 不同。放到独立的 MCP Server 后可以单独扩缩容、单独升级，不影响 Agent 主服务。
- 而文件操作、终端操作依赖宿主机本地环境，知识库查询依赖 RAG 基础设施（PGVector、ES），这些跟 Agent 耦合紧密，保留在本地。

MCP（Model Context Protocol）是一个标准化协议，Agent 端通过 `ToolCallbackProvider` 自动发现 MCP Server 暴露的工具。在代码中，我在 `ToolRegistration` 配置类将本地工具和 MCP 工具统一合并为 `allTools` 数组，对 ReAct 循环来说是透明的——LLM 不需要知道工具是本地的还是远程的。

---

### Q4：ReAct 循环中如果 LLM 陷入死循环怎么办？比如反复调用同一个工具？

**回答：**

我做了几层防护：
1. **maxSteps 硬限制**：最多 10 步强制结束，到达上限会输出"达到最大步骤"的提示。
2. **TerminateTool 引导**：在 nextStepPrompt 中明确告诉 LLM "如果任务已完成或无需进一步操作，请调用 terminate 工具结束交互"，引导 LLM 主动终止。
3. **状态机控制**：AgentState 有 IDLE/RUNNING/FINISHED/ERROR 四种状态，一旦进入 FINISHED 或 ERROR 就不会继续循环。

## 二、意图识别与动态路由

### Q1：你的"规则前置 + LLM 兜底"具体是怎么分层的？为什么不全部用 LLM 做分类？

**回答：**

分层设计的核心动机是**减少不必要的 LLM 调用，降低延迟和成本**。

规则层非常轻量：
- 对于15字以内的短文本，做关键词精确匹配（"你好"、"谢谢"、"再见"等 30+ 个寒暄词）
- 用正则匹配"你是谁"、"你叫什么"这类固定句式

这些场景占比不低（用户经常打招呼、表达感谢），但意图非常明确，完全不需要调用 LLM。规则命中后直接返回 CHAT 意图，延迟几乎为零。

只有规则未命中时才调用 LLM（使用 qwen-turbo 轻量模型，temperature=0），通过 Few-Shot Prompt 让 LLM 在 CHAT/KNOWLEDGE/TASK/REJECT 四个枚举中选一个。

如果全部用 LLM，每次"你好"都要消耗一次模型调用，增加 200-500ms 延迟和 Token 成本，这在高频场景下是不划算的。

---

### Q2：意图分类完之后，不同意图的处理策略有什么区别？对系统性能有什么影响？

**回答：**

四种意图对应四种完全不同的执行路径：

| 意图 | 处理策略 | 工具调用 | LLM 调用次数 |
|------|----------|----------|------------|
| REJECT | 直接返回固定话术 | 无 | 0 |
| CHAT | 一次性 LLM 直答 | 无 | 1 |
| KNOWLEDGE | RAG 检索 + LLM 生成 | 仅知识库工具 | 1 |
| TASK | 完整 ReAct 循环 | 全部工具可用 | 1~10 |

性能影响非常显著：
- REJECT 和 CHAT 完全不进入 ReAct 循环，不调用任何工具，响应速度最快
- KNOWLEDGE 跳过 ReAct，直接调用 RAG 链路后一次性生成答案，比走 ReAct（think→选知识库工具→act→再 think→终止）少了至少 2 次 LLM 调用
- TASK 才走完整的多步循环，全工具可用

这样做的价值是：**80% 的对话（闲聊 + 知识问答）可以用更短的路径完成，只有真正复杂的任务才走重量级的 ReAct 循环**。

---

### Q3：KNOWLEDGE 意图处理失败时你怎么处理？

**回答：**

我设计了**降级机制**：如果 KNOWLEDGE 路径执行异常（比如知识库服务不可用、检索结果为空等），会自动降级到 TASK 意图走完整的 ReAct 循环。这时 Agent 可以自主决定用搜索引擎等其他工具来回答用户问题。

代码中通过 try-catch 包裹 KNOWLEDGE 处理逻辑，异常时直接调用 `handleTaskIntent()`，保证不会因为某个链路故障就返回错误给用户。

---

### Q4：查询重写在整个流程中处于什么位置？为什么要在意图分类之前做重写？

**回答：**

查询重写在 `preProcess` 阶段执行，位于意图分类之前。流程是：用户原始输入 → 查询重写 → 意图分类 → 路由分发。

先重写再分类的原因：多轮对话中用户可能说"它的分数线是多少"，如果直接拿这句话做意图分类，LLM 可能判断为 CHAT（因为太短、太模糊）。但经过重写，变成"南京大学信息管理学院2024年考研分数线是多少"，意图就非常明确是 KNOWLEDGE。

重写的核心逻辑：取最近 10 条对话历史，和当前问题一起发给 LLM，让它输出一句消除指代、补全背景的完整查询。如果没有历史（第一轮对话），直接返回原文，避免无意义的 LLM 调用。

## 三、多路混合检索与重排序

### Q1：为什么要用"向量检索 + BM25"双路召回，而不是只用向量检索？

**回答：**

向量检索和 BM25 各有优劣，互补性很强：

- **向量检索（PGVector）**：基于语义相似度，能理解同义词和语义变换（比如"学费"和"收费标准"），但对精确关键词匹配较弱（比如搜"张三教授"，向量可能返回其他教授的信息）。
- **BM25（Elasticsearch）**：基于词频统计，擅长精确关键词匹配，但不理解语义（"就业率"和"毕业生工作情况"BM25 认为无关）。

双路召回能兼顾语义理解和精确匹配，显著提高召回率。举个实际例子：用户问"信管院出国读研的同学多吗"，向量检索能通过语义找到"留学深造比例"相关文档，BM25 能通过"出国"、"读研"关键词找到具体数据。两者合并后覆盖更全。

---

### Q2：RRF 融合算法具体是怎么工作的？为什么选 RRF 而不是简单的分数归一化后加权？

**回答：**

RRF（Reciprocal Rank Fusion）的公式是：`RRF_score(d) = Σ 1/(k + rank_i(d))`

其中 k=60（标准值），rank 是文档在各路检索中的排名位置（从1开始）。

比如文档 A 在向量检索排第 2，BM25 排第 5：
- RRF_score = 1/(60+2) + 1/(60+5) = 0.0161 + 0.0154 = 0.0315

选 RRF 而不是分数加权的原因：**两路检索的分数不在同一量纲**。向量检索返回的是余弦相似度（0~1），BM25 返回的是 TF-IDF 分数（可能是几十甚至上百），直接归一化会引入人为偏差（归一化范围怎么选？）。

RRF 的优势是**只依赖排名而不依赖具体分数**，天然规避了异构分数融合的问题。而且 k=60 的平滑效果能让排名靠后的文档也有合理的贡献，不会被前几名垄断。

---

### Q3：Rerank 阶段为什么还需要重排序？RRF 融合后的结果不够好吗？

**回答：**

RRF 是一个**粗排**阶段，它只基于排名位置做融合，没有真正理解 query 和 document 之间的语义关系。

Rerank 使用的是交叉编码器（Cross-Encoder，我用的是 gte-rerank-v2 模型），它的原理是将 query 和每个候选文档拼接后一起送入 Transformer，计算**精确的相关性分数**。这比向量检索（Bi-Encoder，query 和 doc 分别编码再算余弦）的精度高得多，因为交叉编码器能捕捉 query 和 doc 之间的细粒度交互。

但交叉编码器的缺点是计算量大（每对 query-doc 都要过一次模型），所以不能对全量文档做 Rerank。我的设计是：
1. 双路各召回 15 条 → RRF 融合后取 15 条（粗排，快速缩小范围）
2. Rerank 对这 15 条精排 → 返回 Top 5（精排，保证质量）

这是业界标准的"漏斗式"检索架构：召回（大量低精度）→ 粗排 → 精排（少量高精度）。

---

### Q4：你的文档分块策略是怎么设计的？为什么要用"结构化分块 + 递归分块"两级？

**回答：**

我的知识库是 Markdown 格式的学院文档，有清晰的标题层级结构。

**第一级：结构化分块（MarkdownStructureSplitter）**
- 按 Markdown 标题（# ~ ######）切分，每个标题下的内容作为一个逻辑块
- 将标题文本写入 metadata 的 `header_context` 字段，这样即使内容片段脱离上下文，也知道它属于哪个主题

**第二级：递归 Token 分块（TokenTextSplitter）**
- 对于标题下内容过长的块（超过 500 tokens），再进行 Token 级别的切分，重叠 100 tokens
- 重叠是为了避免语义在分块边界处被截断

为什么要两级？单纯按 Token 切分会破坏文档的语义结构（可能把属于不同主题的内容切到同一个块里）。先按标题切分保证了每个块的语义内聚性，再按 Token 切分解决了单块过大导致向量检索精度下降的问题。

另外，分块后我还做了 **AI 关键词增强**（KeywordEnricher）：用 LLM 为每个块提取 5 个关键词，拼接到正文前面。这样做的好处是让 Embedding 向量也包含关键词信息，提升向量检索对关键词查询的敏感度。

---

### Q5：BM25 检索时你对哪些字段做了搜索？为什么要加权？

**回答：**

我对 ES 中的三个字段做了多字段加权检索（multi_match）：
- `content^1.0`：文档正文，基础权重
- `keywords^2.0`：AI 提取的关键词，权重最高（关键词是内容的高度浓缩，命中关键词说明强相关）
- `headerContext^1.5`：标题上下文，中等权重（标题通常概括了整段内容的主题）

这种加权设计让 BM25 不仅匹配正文，还能利用结构化元信息提升检索精度。比如用户搜"保研"，如果某个文档的标题就是"保研政策"，即使正文中"保研"出现次数不多，也会因为标题命中而获得更高分数。

## 四、会话记忆与自适应压缩

### Q1：为什么用 Redis 存会话记忆？内存里存不行吗？

**回答：**

纯内存存储有两个致命问题：
1. **服务重启丢失**：Java 应用重启后内存清空，用户回来发现对话历史全没了
2. **多实例不共享**：如果做了水平扩展（多个 Pod），请求可能被分到不同实例，内存记忆不互通

Redis 解决了这两个问题：持久化保证重启不丢，集中存储保证多实例可访问同一会话。

存储结构上，我用 Redis List 存消息：RPUSH 追加新消息、LRANGE 取最近 N 条、LTRIM 控制总量上限。每次读写都续期 TTL（24小时），活跃会话自动续命，僵尸会话自动过期清理，不需要额外的定时任务。

---

### Q2：你提到用 Lua 脚本保证原子性，具体解决什么问题？

**回答：**

如果用普通的 Redis 命令序列（RPUSH → LTRIM → EXPIRE），在并发场景下可能出现：
- 线程 A 执行了 RPUSH，还没来得及 LTRIM
- 线程 B 也执行了 RPUSH
- 结果列表暂时超过了 maxMessages 限制

虽然最终会被 TRIM 修正，但在那个时间窗口内，`get()` 读取到的消息数可能超出预期。

通过 Lua 脚本，RPUSH + LTRIM + EXPIRE 在 Redis 服务端原子执行，没有中间状态暴露。同样，存储级压缩的 `replace` 操作（DEL + RPUSH + EXPIRE）也用 Lua 保证原子性——不会出现 DEL 之后、RPUSH 之前，另一个请求读取到空列表的情况。

---

### Q3：Token 感知的自适应压缩具体是怎么工作的？什么时候触发？

**回答：**

压缩机制作为 Spring AI 的 Advisor（拦截器）实现，在每次请求发给 LLM 之前执行检查。

核心流程：
1. **Token 估算**：遍历消息列表，按 `字符数 × 1.5` 粗略估算总 Token（中文 1 字 ≈ 1.5 token）
2. **预算判断**：预算是 8000 tokens（根据场景推算：混合对话约 800 token/轮 × 目标 10 轮）
3. **触发压缩**：超过 8000 时启动压缩
4. **计算切割点**：从最早的消息开始累加 token，直到累加量 ≥ 超出量 + 缓冲量（30% 预算 = 2400 tokens）
5. **生成摘要**：将切割出的早期消息用轻量模型（qwen-turbo）异步生成一条摘要
6. **重组消息**：摘要（作为 SystemMessage）+ 保留的近期消息 = 压缩后的消息列表
7. **回写 Redis**：将压缩后的列表通过 `replace()` 原子回写，实现存储级压缩

---

### Q4：为什么要设计 30% 的缓冲区？不设缓冲直接压到预算线以下不行吗？

**回答：**

如果刚好压缩到 8000 token 的边界，下一轮对话加入新消息（假设 800 token），立刻就又超出预算，又要触发一次压缩。这导致**频繁压缩**，每轮对话都要调用一次摘要模型，增加延迟和成本。

设计 30% 缓冲（2400 tokens）后，压缩完剩余约 5600 tokens，可以承受约 3 轮新增对话才再次触发。这样压缩频率大幅降低，用户在连续多轮对话中几乎感知不到压缩带来的额外延迟。

这是典型的"批处理思想"——一次多压缩一点，避免频繁触发。

---

### Q5：摘要生成为什么用异步？如果摘要失败了怎么办？

**回答：**

摘要生成要调用 LLM（qwen-turbo），通常需要 2-5 秒。如果同步执行，用户在这段时间看不到任何响应，体验很差。异步执行 + 超时控制（10 秒）可以将影响控制在可接受范围内。

降级策略：
- **超时降级**：超过 10 秒直接取消 Future，使用 fallback 简单截断（保留每条消息前 100 字拼接）
- **异常降级**：LLM 调用失败也走 fallback

fallback 摘要虽然质量不如 LLM 生成的，但至少保留了关键信息片段，不会导致上下文完全丢失。而且这种情况极少发生（模型服务通常可用），正常流程下都是 LLM 生成的高质量摘要。

---

### Q6：你说是"存储级压缩"，和只在内存中压缩有什么区别？

**回答：**

如果只在内存中压缩（请求级别），每次新请求来时从 Redis 读取完整历史，在内存中做压缩后发给 LLM，但 Redis 中的数据不变。这会导致：
- Redis 中的消息列表持续膨胀，最终达到 maxMessages 上限被 LTRIM 暴力截断（丢失中间信息）
- 每次请求都要重新做压缩计算，浪费算力

存储级压缩是：压缩后通过 `replace()` 方法将结果**原子写回 Redis**。这样：
- Redis 中存储的就是压缩后的精简数据，存储空间始终可控
- 下次请求读取时已经是压缩后的，不需要重复压缩
- 摘要作为 SystemMessage 持久化，成为后续所有请求的"历史共识"
