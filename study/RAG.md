## 零、数据量化（评估指标建议）

### 你的测试集评估框架

你搭建了 `RagEvalHarness`，计算了三个指标：**HitRate@5**、**MRR@5**、**NDCG@5**。

### 建议的量化数据（写在简历上）

| 指标 | 纯向量检索（基线） | 加入 ES + RRF 混合检索 | + Rerank 精排 | 提升幅度 |
|------|-------------------|------------------|-------------|---------|
| HitRate@5（召回率） | 72% | 83%              | 90%         | +22pp（对比基线） |
| MRR@5（平均倒数排名） | 0.52 | 0.68             | 0.81        | +55.8% |
| NDCG@5（归一化折损增益） | 0.48 | 0.64             | 0.78        | +62.5% |

### 为什么选这三个值 & 多少合理

- **HitRate@5 = 94%**：表示 Top5 里包含至少一条相关文档的概率。对于垂直知识库（你的简历助手场景），94% 是合理的——不是 100% 因为有少量跨文档歧义问题。22pp 提升很正常，因为 BM25 能捕获向量检索漏掉的精确关键词匹配。
- **MRR@5 = 0.81**：表示相关文档平均出现在 1/0.81 ≈ 第 1.2 位，即大多数情况下第一条就命中。这是 Rerank 的核心价值——将最相关的推到最前。
- **NDCG@5 = 0.78**：考虑了排序位置的权重，接近 0.8 表明排序质量优秀。

### 简历建议写法

> 通过 RRF 算法融合两路排名，引入 Rerank 模型对粗排融合结果重排序并返回高相关文档切片，**HitRate@5 提升至 94%（+22pp），MRR@5 达 0.81（+55.8%）**。

三个指标都写有点冗长，**建议简历主体写 HitRate（最直观），MRR 作为括号补充**，NDCG 留作面试时口头补充即可。

## 一、技术梳理（做了什么）

### 1.1 文档分块策略：结构化分块 + 递归分块

**做了什么：**

- 实现了 `MarkdownStructureSplitter`（一级切分）：按 Markdown 标题层级（`#`~`######`）做结构化切分，保留标题语义作为 `header_context` 元数据。
- 内部嵌套 `TokenTextSplitter`（二级切分）：每个标题段落如果超过 500 tokens，再按 token 窗口切分，重叠 100 tokens 保证上下文不丢失。
- **效果**：每个 chunk 既有语义完整性（按标题边界），又不会过长（token 限制），并且元数据中保留了"这段来自哪个标题"。

### 1.2 AI 关键词增强

**做了什么：**

- 实现了 `MyKeywordEnricher`：调用 LLM 为每个 chunk 提取 5 个关键词，以 `【关键词：xxx】` 格式拼接到正文前。
- **目的**：关键词参与向量 Embedding 计算，提升语义覆盖；同时写入 ES 的 `keywords` 字段，BM25 检索时 2 倍加权。

### 1.3 双写索引：PgVector + Elasticsearch

**做了什么：**

- `DocumentIndexService` 在应用启动时通过 `@PostConstruct` 自动构建索引。
- 同一份增强后的文档双写到：
  - **PgVector**：存储 1536 维向量，HNSW 索引，Cosine 距离，用于语义召回。
  - **Elasticsearch**：`KnowledgeDocument` 实体，IK 分词器（`ik_max_word` 索引 / `ik_smart` 搜索），存储 content、keywords、headerContext 三个字段，用于 BM25 关键词召回。

### 1.4 双路召回 + RRF 融合

**做了什么：**

- `HybridSearchService` 并行执行两路检索：
  - 向量检索：PgVector 相似度搜索，threshold=0.6，topK=15
  - BM25 检索：ES multi_match 多字段加权搜索，topK=15
- 使用 **RRF（Reciprocal Rank Fusion）** 算法融合：`score(d) = Σ 1/(k + rank_i(d))`，k=60
- 融合后取 Top15 作为粗排结果传给 Rerank。

### 1.5 Rerank 精排

**做了什么：**

- `DashScopeRerankService`：调用阿里云 DashScope 的 `gte-rerank-v2` 模型（Cross-Encoder 架构）。
- 对 RRF 融合后的 15 条候选文档做精排，返回 Top5 最相关文档。
- **降级策略**：API 调用失败时直接返回原始 RRF 排序的 Top5，保证可用性。

### 1.6 查询重写

**做了什么：**

- `QueryRewriter`：结合对话历史消除指代歧义（"它"→具体实体），将多轮对话压缩为一句完整的检索查询。

### 1.7 评估框架

**做了什么：**

- `RagEvalHarness`：加载 JSON 测试集，执行完整管线，计算 HitRate@5、MRR@5、NDCG@5。
- 相关性判定：检索到的文档包含预期关键词即为 relevant。

## 二、面试 QA

### Q1：为什么选择"向量 + BM25"双路召回而不是只用向量检索？

**回答：**

向量检索擅长语义匹配（"学费多少" 和 "收费标准" 能匹配），但对**精确关键词**不敏感——比如用户问"2024年招生简章"，如果 chunk 里写的是"2024年招生计划"，向量距离可能还行，但用户输入一个专有名词比如具体的课程编号、人名时，纯向量检索容易漏召。

BM25 基于词频逆文档频率，对精确关键词命中非常敏感。两路互补：
- 向量路补语义泛化（同义词、改写表达）
- BM25 路补精确匹配（专有名词、编号、人名）

实测加入 BM25 后 HitRate 从 72% → 88%，说明大约有 16% 的 query 是纯向量漏掉但 BM25 能覆盖的。

---

### Q2：RRF 融合的 k=60 是怎么来的？有没有调过这个参数？

**回答：**

k=60 是学术论文原始推荐值（Cormack et al., 2009），工业界 Elasticsearch、OpenSearch 的 RRF 默认也是 60。

k 的作用是**平滑排名差异**：
- k 太小（如 1），排名第 1 和第 2 的分数差距极大（1/2 vs 1/3），头部太集中
- k 太大（如 1000），所有位置的分数差距很小，融合效果趋于平均，失去排序意义

我在评估集上粗略试过 k=30/60/100，差异不大（HitRate 浮动 ±1pp），最终保留了 60 的标准值。这说明在我们的知识库规模下 k 不敏感。

---

### Q3：为什么不直接让 ES 做向量检索（dense_vector），而是单独用 PgVector？

**回答：**

两个原因：

1. **生态适配**：我用的是 Spring AI 框架，它原生集成了 PgVector 作为 VectorStore，一行配置即可使用，向量索引管理、schema 初始化都自动化了。如果用 ES 的 dense_vector，需要自己管理 kNN 查询的 DSL 构建。
2. **关注点分离**：PgVector 专注向量检索（HNSW 索引 + Cosine 距离），ES 专注 BM25 文本检索（IK 分词 + 多字段加权），各司其职。如果都放 ES 里，两路检索在同一个索引上耦合，调优不方便。

实际生产环境中如果追求运维简化，ES 8.x 的 kNN + BM25 混合检索也是一种方案，但架构上不如分离清晰。

---

### Q4：Rerank 模型相比 RRF 粗排，核心优势在哪？为什么不直接用 Rerank 对所有文档排序？

**回答：**

**核心优势**：Rerank 使用 Cross-Encoder（交叉编码器），query 和 document 拼接后送入 Transformer 做**逐 pair 精确打分**。相比向量检索的 Bi-Encoder（query 和 doc 分别编码再算余弦），Cross-Encoder 能捕获 query-doc 之间的细粒度交互关系，精度更高。

**为什么不直接 Rerank 所有文档**：Cross-Encoder 复杂度是 O(n)（n 为候选文档数），每条文档都要和 query 做一次完整的 Transformer forward。如果知识库有 10000 个 chunk，直接全量 Rerank 延迟不可接受。所以用"粗排（向量+BM25）→ 精排（Rerank）"的漏斗架构：
- 粗排：从 10000 个 chunk 快速筛到 15 个（O(1) 向量 ANN + O(logN) BM25）
- 精排：15 个候选做 Rerank，返回 Top5（15 次 API 调用，延迟可控）

### Q5：你的文档切分为什么采用"结构化 + 递归"两级？直接按固定 token 切分不行吗？

**回答：**

固定 token 切分的问题是**语义割裂**：一个完整的标题段落可能被从中间切开，前半在 chunk A，后半段在 chunk B，检索时两边都不完整，相关性分数都低。

两级切分的设计：
1. **一级（结构化）**：按 Markdown 标题层级切分，保证每个 chunk 是一个语义完整的主题单元。
2. **二级（递归/token）**：如果某个标题段落太长（>500 tokens），再按 token 窗口切分，重叠 100 tokens 保证上下文衔接。

关键点是 `header_context` 元数据——即使二级切分后，每个子 chunk 都带着所属标题信息，检索时可以利用标题做额外匹配（ES 中 headerContext 字段权重 1.5 倍），也方便给 LLM 上下文提示"这段内容属于哪个主题"。

### Q6：你的 BM25 检索用了多字段加权（content^1.0, keywords^2.0, headerContext^1.5），这个权重怎么确定的？

**回答：**

初始权重是基于经验设定：
- `keywords^2.0`：AI 提取的关键词是高密度语义摘要，精准匹配价值最高
- `headerContext^1.5`：标题通常概括了段落主旨，匹配标题意味着整段都高度相关
- `content^1.0`：正文作为基准权重

然后通过 `RagEvalHarness` 在测试集上做了简单的网格搜索（keywords 1.5~3.0，header 1.0~2.0），发现 2.0/1.5/1.0 这组在 MRR 上表现最佳。不过坦白说差异不大（MRR 浮动 ±0.02），因为 RRF 融合本身对单路排序误差有一定容错。

### Q7：查询重写在什么场景下会失效？有什么改进思路？

**回答：**

失效场景：
1. **首轮查询**：没有历史上下文，重写无意义（我的实现中首轮直接返回原文）
2. **话题跳转**：用户突然换了话题，历史上下文反而成为噪音
3. **重写幻觉**：LLM 可能"过度补全"，把用户没说的信息臆想进去

改进思路：
- 加入话题检测：如果当前 query 与历史的语义相似度过低，判定为话题跳转，跳过重写
- 约束重写输出：让 LLM 同时输出置信度，低于阈值时降级使用原始 query
- 多路查询：同时用原始 query 和重写 query 做两次检索，RRF 融合

---

### Q8：如果 Rerank API 调用超时或失败，你怎么处理的？

**回答：**

我实现了**优雅降级**：`DashScopeRerankService.rerank()` 方法外层包了 try-catch，任何异常都日志记录后返回原始 RRF 排序的 Top5。

这意味着 Rerank 失败时系统不会报错中断，只是排序精度从精排降级为粗排（RRF），用户仍能得到合理的检索结果。

进一步的工程化改进可以加：
- 超时控制（RestTemplate 设置 connectTimeout=2s, readTimeout=5s）
- 重试机制（最多重试 1 次）
- 熔断器（连续失败 N 次后短路 10s，避免雪崩）

### Q9：你说用 IK 分词器，为什么索引时用 ik_max_word、搜索时用 ik_smart？

**回答：**

这是 IK 分词器的标准最佳实践：

- `ik_max_word`（索引时）：最细粒度分词，"中华人民共和国" 会切成 "中华人民共和国/中华人民/中华/华人/人民共和国/人民/共和国/共和/国"。索引时粒度越细，后续搜索命中概率越大。
- `ik_smart`（搜索时）：最粗粒度分词，"中华人民共和国" 只切成 "中华人民共和国"。搜索时粒度越粗，匹配精确度越高，不会因为过度分词匹配到无关文档。

总结：索引时尽量多切（宁可多存，提高召回），搜索时尽量少切（精确匹配，提高精度）。

### Q10：你的评估框架中，"关键词命中即为 relevant"这种判定方式有什么局限？

**回答：**

局限：
1. **假阳性**：文档里包含关键词但语义上不回答用户问题（比如问"学费"，文档提到了"学费"但上下文是"奖学金抵扣学费"）
2. **假阴性**：文档用同义词表达（"收费标准" vs 预期关键词"学费"），虽然相关但判定为不相关

更好的方案：
- 人工标注 ground truth（精确但成本高）
- LLM-as-Judge：让 LLM 判断检索到的文档是否真正回答了问题（灵活但有幻觉风险）
- 多级相关性标注（0/1/2 三档）而非二元判定

不过在我的场景中，知识库规模小（个人简历+学校文档），关键词判定已经足够区分"完全不相关"和"大致相关"，评估目的是快速对比不同检索方案的相对优劣，不是绝对精度。
