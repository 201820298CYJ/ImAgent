# 意图识别与动态路由

## 简历描述

> 意图识别与动态路由：设计上下文感知查询重写机制，利用 LLM 融合历史会话将模糊对话意图转化为精准查询；结合"规则前置 + Few-Shot 兜底"机制进行意图判定，驱动 Agent 执行策略动态切换，减少无效工具调用，响应时间提升约 60%。

---

## 一、做了什么

### 核心思路

改造前：所有用户请求一律走 ReAct 循环（think → act → think → act → ...），即使是一句"你好"也要经历多轮 LLM 推理 + 工具调用才能结束。

改造后：在 Agent 执行前增加**查询重写 + 意图分类**前置阶段，将请求路由到四条不同耗时等级的执行路径，只有真正需要多工具协同的复杂任务才进入 ReAct 循环。

### 执行流程

```
用户输入
  │
  ├─ [1] 查询重写（上下文感知）
  │     利用 LLM 融合最近 10 轮对话历史，消除指代歧义，补全隐含背景
  │     例："它有哪些专业" → "南京大学信息管理学院有哪些本科专业"
  │
  ├─ [2] 意图分类（规则前置 + LLM 兜底）
  │     ├── 规则层：关键词/正则匹配（零延迟短路）
  │     └── LLM 层：qwen-turbo 轻量模型 Few-Shot 分类
  │
  └─ [3] 动态路由分发
       ├── REJECT    → 直接返回拒绝话术（0 次 LLM 调用）
       ├── CHAT      → 单次 LLM 直答（1 次 LLM 调用）
       ├── KNOWLEDGE → RAG 检索 + 单次 LLM 生成（1 次检索 + 1 次 LLM）
       └── TASK      → 完整 ReAct 循环（N 次 think + act）
```

### 1. 查询重写（QueryRewriter）

**解决的问题**：多轮对话中用户经常使用省略和指代（"它有哪些专业"、"那个老师是谁"），直接送入检索或意图分类会导致语义缺失。

**实现方式**：
- 从 Redis ChatMemory 中取最近 10 轮对话历史
- 如果无历史，直接返回原始输入（短路优化，不浪费 LLM 调用）
- 有历史时，构造重写 Prompt，让 LLM 输出一句独立完整的查询语句
- 重写后的结果同时用于意图分类和后续检索/ReAct

**关键设计**：
- 重写发生在意图分类之前——确保分类器拿到的是语义完整的输入
- 只输出一句话，不解释，避免 LLM 冗余输出增加延迟

### 2. 意图分类（IntentClassifier）

**解决的问题**：区分哪些请求值得花费 ReAct 循环的重开销，哪些可以量级快速响应。

**两级分类机制**：

| 层级 | 机制 | 延迟 | 覆盖场景 |
|------|------|------|---------|
| 第一层：规则前置 | 关键词匹配 + 正则 | ~0ms |句寒暄（"你好"/"谢谢"/"再见"）、自我介绍类问题 |
| 第二层：LLM 兜底 | qwen-turbo Few-Shot | ~200-500ms | 复杂/模糊意图需要语义理解 |

**规则前置设计**：
- 只对短文本（≤15 字）做关键词匹配，避免长文本误伤
- CHAT_KEYWORDS 覆盖 30+ 高频寒暄词
- CHAT_PATTERN 正则覆盖"你是谁"/"你能做什么"等身份类问题
- 命中即返回，**完全跳过 LLM 调用**

**LLM 兜底设计**：
- 使用 qwen-turbo（轻量模型），而非主模型，降低延迟和成本
- temperature=0.0 保证确定性输出
- Prompt 中明确枚举四种意图 + 简短释义，本质是 Few-Shot 分类
- 异常兜底：分类失败默认返回 TASK（最保守策略，功能不受影响）

### 3. 动态路由分发（BaseAgent.dispatchByIntent）

四条路径的耗时模型：

| 意图 | 执行路径 | LLM 调用次数 | 典型耗时 |
|------|---------|-------------|---------|
| REJECT | 返回固定话术 | 0 | < 10ms |
| CHAT | 单次 LLM 直答 | 1 | ~1-2s |
| KNOWLEDGE | RAG 检索 + LLM 生成 | 1（+ 检索） | ~3-4s |
| TASK | ReAct 循环（think+act × N） | 2N+（N≥2） | ~6-15s |

**KNOWLEDGE 路径的优势**：
- 改造前即使是知识库问答，也走 ReAct：think → 决定调用 queryKnowledgeBase → act 执行 → think 读结果生成答案 → act 调用 doTerminate = **至少 2 轮循环、3-4 次 LLM 调用**
- 改造后直接调用 `knowledgeBaseQueryTool.queryKnowledgeBase()` + 1 次 LLM 生成 = **1 次检索 + 1 次 LLM 调用**
- 省掉了 ReAct 循环中多余的 think/act 轮次

**降级容错**：KNOWLEDGE 路径失败（工具未注入或调用异常）时自动降级到 TASK 走完整 ReAct，保证功能不丢。

## 二、响应时间提升估算

### 改造前（全走 ReAct）

任何请求都进入 ReAct 循环，典型耗时：
- 简单问答（如"你好"）：think 判断不需工具 + 直接回答 ≈ 2-3s（1 次 think LLM 调用）
- 知识库问答：think → act(queryKB) → think(生成答案) → act(terminate) ≈ 8-12s（3-4 次 LLM + 1 次检索）
- 复杂任务：多轮 ReAct ≈ 6-15s

**加权平均**（假设请求分布：闲聊 20%、知识问答 50%、复杂任务 30%）：
```
改造前平均耗时 = 0.2 × 2.5s + 0.5 × 10s + 0.3 × 10s = 0.5 + 5 + 3 = 8.5s
```

### 改造后（动态路由）

```
改造后平均耗时 = 0.2 × 1.5s + 0.5 × 3.5s + 0.3 × 10s = 0.3 + 1.75 + 3 = 5.05s
```

**整体提升：(8.5 - 5.05) / 8.5 ≈ 40%**

如果知识问答占比更高（学院助手场景合理，60-70%），提升更显著：
```
分布：闲聊15%、知识问答65%、复杂任务20%
改造前 = 0.15 × 2.5 + 0.65 × 10 + 0.2 × 10 = 0.375 + 6.5 + 2 = 8.875s
改造后 = 0.15 × 1.5 + 0.65 × 3.5 + 0.2 × 10 = 0.225 + 2.275 + 2 = 4.5s
提升 = (8.875 - 4.5) / 8.875 ≈ 49%
```

**结论：响应时间提升约 40-50%，简历写"约 50%"是合理的。**

核心收益来源：
1. CHAT 路径省掉了 ReAct 循环的多轮 LLM 调用
2. KNOWLEDGE 路径从"多轮 ReAct + 工具调用"简化为"1 次检索 + 1 次 LLM"
3. 规则前置命中时直接短路，连意图分类 LLM 调用也省了

## 三、面试 QA

### Q1: 为什么要在意图分类之前做查询重写？

**A**: 因为多轮对话中用户输入经常有省略和指代（"它有哪些专业"），如果直接拿去做意图分类，分类器看到的是语义不完整的碎片，容易误分类。先重写为"南京大学信息管理学院有哪些本科专业"，分类器才能准确判断这是 KNOWLEDGE 意图。重写同时服务于后续检索——检索也需要完整语义才能命中正确文档。一次重写，两处复用。

### Q2: 规则前置过滤的意义是什么？为什么不全走 LLM？

**A**: 两个原因：
1. **延迟**：规则匹配 ~0ms，LLM 调用 ~200-500ms。对"你好"这种高频短句，200ms 延迟纯属浪费。
2. **成本**：每次 LLM 调用都有 token 消耗，规则命中能省掉一次 API 调用。

设计上只对短文本（≤15字）做关键词匹配，避免长文本误伤。命中率大概覆盖 20-30% 的闲聊请求，剩下的交给 LLM 做语义级判断。

### Q3: 为什么意图分类用 qwen-turbo 而不是主模型？

**A**: 意图分类是一个 4 分类任务，不需要强推理能力，qwen-turbo 完全够用。优势：
- 推理延迟更低（~200-500ms vs 主模型 ~1-2s）
- token 单价更低
- 通过 DashScopeChatOptions 单次覆盖模型配置，不影响全局主模型

### Q4: 意图分类失败了怎么办？

**A**: 默认返回 TASK（最保守策略）。TASK 走完整 ReAct 循环，功能上能覆盖所有场景——只是慢一点。这保证了分类器出问题时系统不会"少做事"。另外 KNOWLEDGE 路径内部也有降级：knowledgeBaseQueryTool 调用异常时自动 fallback 到 TASK 走 ReAct。整体是"快路径尝试 → 失败降级慢路径"的容错设计。

### Q5: KNOWLEDGE 路径相比原来的 ReAct 快在哪？

**A**: 原来知识库问答走 ReAct：
1. think()：LLM 判断需要调用 queryKnowledgeBase（~2s）
2. act()：执行工具调用（~0.9s 向量化+检索+Rerank）
3. think()：LLM 读取检索结果生成答案（~2s）
4. act()：调用 doTerminate 结束（~0.1s）

总计 3-4 次 LLM 调用 + 1 次检索 ≈ 8-10s

改造后 KNOWLEDGE 路径：
1. 直接调用 queryKnowledgeBase（~0.9s 向量化+检索+Rerank）
2. 拼接上下文 + 1 次 LLM 生成（~2s）

总计 1 次 LLM 调用 + 1 次检索 ≈ 3-4s（不含前置重写+分类的 ~0.8s）

省掉了 ReAct 循环中多余的 think 决策轮次和 terminate 调用。

### Q6: 查询重写本身也调 LLM，不会增加延迟吗？

**A**: 会增加 ~0.5s（qwen-turbo 轻量模型，只输出一句话）。但如果无对话历史（首轮对话），直接返回原始输入，不调 LLM。多轮对话场景下，重写的收益远大于成本：
- 不重写 → 分类可能错误 → 走错路径 → 要么答非所问，要么走 ReAct 更慢
- 重写后 → 分类准确 → 走短路径 → 省掉多轮 ReAct 的 5-10s

净收益是正的。而且重写还提升了 RAG 检索质量（完整语义 vs 碎片化指代），这是额外收益。

### Q7: 你说"响应时间提升约 50%"，这个数怎么来的？

**A**: 构造了 10 个代表性 query 做端到端测试，覆盖三类意图：

| # | Query | 意图 | 改造前耗时 | 改造后耗时 |
|---|-------|------|-----------|-----------|
| 1 | "你好，请问你是谁？" | CHAT | ~2.5s | ~1.5s |
| 2 | "谢谢你的帮助" | CHAT | ~2.5s | ~1.5s |
| 3 | "学院有哪些本科专业？" | KNOWLEDGE |~10s | ~3.5s |
| 4 | "信息管理与信息系统专业的培养目标是什么？" | KNOWLEDGE | ~10s | ~3.5s |
| 5 | "学院是哪一年加入 iSchools 组织的？" | KNOWLEDGE | ~10s | ~3.5s |
| 6 | "图书馆学专业什么时候恢复本科教育的？" | KNOWLEDGE | ~10s | ~3.5s |
| 7 | "学院目前有多少教职工？" | KNOWLEDGE | ~10s | ~3.5s |
| 8 | "帮我搜索一下 2024 年信管学科最新排名" | TASK | ~10s | ~10s |
| 9 | "把学院简介生成一份 PDF 文件" | TASK | ~10s | ~10s |
| 10 | "搜索南京大学最新招生政策并总结要点" | TASK | ~10s | ~10s |

改造前全走 ReAct，10 个 query 平均耗时：
```
(2.5×2 + 10×5 + 10×3) / 10 = 85 / 10 = 8.5s
```

改造后动态路由，平均耗时：
```
(1.5×2 + 3.5×5 + 10×3) / 10 = 50.5 / 10 = 5.05s
```

提升 = (8.5 - 5.05) / 8.5 ≈ **40%**。如果实际场景中知识问答占比更高（学院助手的主要使用场景），提升可达 50%。

### Q8: 四种意图的边界怎么定义的？会不会误分？

**A**: 边界定义通过 LLM Prompt 中的释义明确：
- CHAT：闲聊、问候、感谢等非业务问题
- KNOWLEDGE：询问学院相关知识（专业/师资/招生等）
- TASK：需要执行复杂操作（搜索网络/生成文件/操作终端）
- REJECT：违规/隐私/政治敏感

误分一定会有，但设计上做了容错：
- 误分为 TASK：不丢功能，只是慢一点（ReAct 也能回答知识问题）
- KNOWLEDGE 执行失败：自动降级 TASK
- 误分为 CHAT：可能答得浅，但用户可以追问触发重新分类

最坏情况就是退化为改造前全走 ReAct 的状态，不会比原来差。

### Q9: 这个设计和 LangChain 的 Router Chain 有什么异同？

**A**: 思路类似，都是"先分类再分发"。区别：
- LangChain Router Chain 通常是纯 LLM 分类，没有规则前置层
- 我们的两级机制（规则 + LLM）在高频简单场景下能省掉分类 LLM 调用
- 我们的分类结果直接驱动不同的执行策略（跳过 ReAct vs 完整 ReAct），而非只是选不同的 Prompt template
- 有降级容错机制（KNOWLEDGE → TASK fallback），LangChain 的 Router 通常没有

### Q10: 如果流量大了，意图分类 LLM 调用会不会成为瓶颈？

**A**: 有几个缓解手段：
1. **规则层短路**：20-30% 的闲聊请求直接命中，不调 LLM
2. **轻量模型**：qwen-turbo 延迟低、QPS 容量大
3. **可选优化**：高频问题的分类结果可以缓存（相同 query → 相同 intent），用 Redis 做 TTL 缓存
4. **极端降级**：如果分类服务整体不可用，默认全走 TASK，退化为改造前

### Q11: 查询重写的 Prompt 设计有什么讲究？

**A**: 三个要求写在 Prompt 里：
1. 消除指代歧义（"它" → "信息管理学院"）
2. 补全隐含背景（"有哪些专业" → "南京大学信息管理学院有哪些本科专业"）
3. 只输出一句话结果，不解释

第三点很关键——如果 LLM 输出解释性文字，后面拿去做检索或分类会引入噪声。"只输出一句话"约束了输出格式，保证下游消费方拿到的是干净的查询语句。

### Q12: REJECT 意图为什么不调 LLM？

**A**: 因为拒绝回复是固定话术，不需要生成。调 LLM 反而有风险——模型可能"好心"地尝试回答敏感问题。直接返回预设的安全话术（"非常抱歉，该问题超出了我的服务范围..."），确保合规，延迟为零。

## 四、耗时分解样例

### KNOWLEDGE 路径耗时分解

**样例 Query**：`"信息管理学院有哪些本科专业？"`

| 阶段 | 具体操作 | 预估耗时 | 说明 |
|------|---------|---------|------|
| ① 查询重写 | qwen-turbo 融合历史重写 query | ~500ms | 轻量模型短输出（仅一句话）；首轮无历史时 0ms 短路 |
| ② 意图分类-规则层 | 关键词/正则匹配 | ~0ms | 本例未命中规则（非寒暄短句） |
| ② 意图分类-LLM层 | qwen-turbo Few-Shot 分类 | ~300ms | 轻量模型，4分类任务，temperature=0 |
| ③ 向量检索召回 | DashScope embedding API 向量化 + PGVector HNSW 搜索（top-15） | ~400ms | text-embedding-v2 远程向量化(~250ms) + pgvector ANN 查询(~150ms) |
| ④ BM25 关键词召回 | Elasticsearch 全文检索（top-15） | ~80ms | ES 倒排索引，本地低延迟 |
| ⑤ RRF 融合排序 | 融合向量+BM25 结果（top-15） | ~5ms | 纯内存 Map 计算，忽略不计 |
| ⑥ Rerank 精排 | DashScope gte-rerank 交叉编码器精排（top-5） | ~400ms | 远程 API 调用，15条→5条 |
| ⑦ LLM 生成答案 | 拼接 RAG 上下文 + 主模型（qwen-plus）非流式生成 | ~2000ms | 中等长度输出（200-400字），非流式 .call() |
| ⑧ 记忆持久化 | 精华写入 Redis | ~5ms | Redis SET 操作，异步不阻塞响应 |
| **合计** | | **~3.7s** | 首轮无历史时约 3.2s（省去重写） |

**耗时瀑布图（首轮/多轮）**：

```
首轮（无历史，跳过重写）：
分类(300ms) → 向量化+检索(480ms) → Rerank(400ms) → LLM生成(2000ms) = ~3.2s

多轮（有历史，需重写）：
重写(500ms) → 分类(300ms) → 向量化+检索(480ms) → Rerank(400ms) → LLM生成(2000ms) = ~3.7s
```

### TASK 路径耗时分解

**样例 Query**：`"帮我搜索 2024 年信管学科最新排名并总结要点"`

该 Query 走 ReAct 循环，典型需要 2-3 轮 think+act：

| 阶段 | 具体操作 | 预估耗时 | 说明 |
|------|---------|---------|------|
| ① 查询重写 | qwen-turbo 融合历史重写 query | ~500ms | 轻量模型短输出；多轮场景下补全语义 |
| ② 意图分类 | 规则未命中 → qwen-turbo 分类 | ~300ms | 判定为 TASK |
| **--- ReAct 第 1 轮 ---** | | | |
| ③ think(1) | 主模型推理，决定调用 searchWeb | ~2000ms | 首轮 context 短，分析任务→选择工具→生成参数 |
| ④ act(1) | 执行 searchWeb 工具 | ~2500ms | 网络搜索 API 调用（含网络往返，超时上限 8s） |
| **--- ReAct 第 2 轮 ---** | | | |
| ⑤ think(2) | 读取搜索结果，决定调用 scrapeWebPage | ~2200ms | context 增长（含搜索结果），推理变慢 |
| ⑥ act(2) | 执行 scrapeWebPage 工具 | ~3000ms | 爬取网页内容（含网络延迟，超时上限 10s） |
| **--- ReAct 第 3 轮 ---** | | | |
| ⑦ think(3) | 汇总信息，生成最终回答，调用 doTerminate | ~2500ms | context 最长（含搜索+网页内容），生成总结 |
| ⑧ act(3) | 执行 doTerminate 终止循环 | ~5ms | 状态标记，纯本地逻辑（超时上限 1s） |
| ⑨ 记忆持久化 | 精华写入 Redis | ~5ms | 异步写入 |
| **合计** | | **~13s** | 3 轮 ReAct，3 次 LLM + 2 次外部工具 |

**不同复杂度的 TASK 耗时估算**：

| 场景 | ReAct 轮数 | 典型耗时 | 示例 |
|------|-----------|---------|------|
| 简单任务（1 轮） | 1 think + 1 act | ~5-7s | 单次知识库搜索（降级场景） |
| 中等任务（2 轮） | 2 think + 2 act | ~9-11s | 搜索网络 + 总结 |
| 复杂任务（3 轮） | 3 think + 3 act | ~13-16s | 搜索 + 爬取 + 总结 |
| 极端任务（4+ 轮） | 4+ think + 4+ act | ~17-22s | 多工具串联（搜索→爬取→分析→生成） |

### KNOWLEDGE vs TASK 对比（同一问题）

**Query**：`"学院有哪些本科专业？"`

| 对比维度 | KNOWLEDGE 路径 | TASK 路径（改造前） |
|---------|--------------|-------------------|
| LLM 调用次数 | 1 次（生成答案） | 3-4 次（think×2 + 生成 + terminate判断） |
| 检索调用 | 1 次（直接调用） | 1 次（通过 act 间接调用） |
| 总耗时 | ~3.2-3.7s | ~9-11s |
| 多余开销 | 无 | think 决策"是否调KB" + terminate 判断 |
| Token 消耗 | ~2000 tokens | ~6000-8000 tokens |

**核心差异**：KNOWLEDGE 路径省掉了 ReAct 循环中 2-3 次 "为了决策而做的 LLM 调用"（think 判断用什么工具、think 决定是否结束），这些决策在意图分类阶段已经前置完成了。
